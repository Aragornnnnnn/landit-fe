# 캐릭터 입모양과 립싱크

대화 화면의 상대 캐릭터가 말할 때 입을 어떻게 움직이는지, 그리고 정확도를 어디까지 올릴 수 있는지 정리한다. 구현 배경은 `~/Developer/rive-poc`의 PoC에서 검증했다.

## 립싱크는 두 부품이다

립싱크를 하나의 기능으로 보면 선택지가 안 보인다. 실제로는 독립된 두 부품이다.

1. **어떤 입모양인가** — 지금 "오" 발음 중이면 둥근 입, "이"면 넓적한 입, "음"이면 다문 입
2. **얼마나 벌리는가** — 같은 "아"라도 외치면 크게, 속삭이면 작게

1번이 본체다. 1번만 있어도 입이 말에 맞춰 움직인다. 2번은 강약을 입혀 생동감을 더하는 보정이고, 없으면 입 크기가 일정해서 다소 기계적으로 보일 뿐 엉뚱하게 움직이진 않는다.

이 구분이 중요한 이유는 **두 부품의 정보 출처가 완전히 다르기 때문**이다. 1번은 텍스트와 재생 시각에서 오고, 2번은 소리 자체를 분석해야 나온다.

## 입을 그리는 방식

입모양을 여러 장 그려두고 갈아끼우는 방식(스왑)은 전환이 튄다. 그래서 원본 입 그림 하나를 두고 **가로·세로 스케일만 매 프레임 보간**한다.

```
비짐 목표(open/round/wide/closed) → 목표 스케일 → 현재값에서 조금씩 다가감
```

세부 규칙 세 가지가 자연스러움을 만든다.

- **최소 유지 시간** — 발음이 너무 빨리 바뀌면 중간을 건너뛴다. 없으면 입이 파닥거린다
- **비대칭 관성** — 벌릴 때는 빠르게, 닫을 때는 천천히. 실제 입의 물리 특성이다
- **턱 드랍** — 벌어질수록 입 전체가 살짝 아래로 내려간다

표정(눈·눈썹)과 립싱크(입)는 **서로 다른 파츠**를 건드리므로 동시에 성립한다. "눈웃음 지으며 말하기"가 별도 작업 없이 된다.

## 타이밍을 어디서 얻는가

핵심 질문은 "지금 이 순간 어떤 발음인가"를 무엇으로 아느냐다. 구현은 이 부분만 갈아끼울 수 있게 분리해 둔다.

```
driveMouth(audio, shapeAt)   ← 입 구동. 어떤 방식이든 안 바뀐다
                ↑
        shapeAt 만 교체한다
```

### 방법 1 — 텍스트 균등 배분 (현재)

문장 철자를 입모양 순서로 바꾸고 오디오 길이에 균등하게 나눈다. 오디오를 분석하지 않으므로 어떤 TTS와도 동작하고 비용이 없다.

한계는 **실제 발음이 균등하지 않다**는 점이다. 강세 모음은 길게 늘어지고 자음은 순식간에 지나가며, 쉼표에서는 소리가 멈춘다. 특히 침묵 구간에도 글자가 배분되어 입이 계속 움직이는 게 눈에 띈다.

### 방법 2 — 음량 그래프로 정렬 개선

오디오를 **재생 전에 디코딩**해 시간별 음량 표를 만들어 둔다. 소리가 나는 구간과 침묵 구간을 알 수 있으므로, 글자를 소리 구간에만 배분한다.

여기서 주의할 점이 있다. 재생 중인 오디오에 분석기를 연결하는 방식(`createMediaElementSource`)은 오디오가 분석기를 거쳐 스피커로 가게 되는데, iOS WebView가 이 경로에서 문제를 일으킬 수 있다. **사전 디코딩은 재생 경로와 분리**되어 있어 이 위험이 없다.

음량만으로는 "무엇을 발음하는지"는 알 수 없다. 침묵·강세만 정확해지고 입모양 선택은 여전히 텍스트 추측이다.

### 방법 3 — 주파수 분석으로 모음 추정

소리를 주파수 대역으로 나누면 대략적인 모음 구분이 가능하다. "이"는 고음 에너지가 세고 "우"는 저음 쪽이다.

다만 정확도가 목소리·언어에 따라 들쭉날쭉해 튜닝 비용이 크다. 텍스트를 이미 갖고 있는 상황에서는 투자 대비 효과가 낮다.

### 방법 4 — 강제 정렬 (STT 재활용)

TTS로 만든 오디오를 STT(Deepgram)에 다시 넣으면 단어별 타임스탬프를 얻는다. 이미 쓰는 벤더로 꽤 정확한 정답지를 만들 수 있다. 대신 합성 후 왕복이 한 번 더 붙어 첫 재생이 느려진다.

### 방법 5 — TTS가 타임스탬프를 함께 준다

일부 TTS는 오디오와 함께 글자별 발음 시각을 응답에 실어 준다. ElevenLabs의 `/with-timestamps` 엔드포인트가 그렇다.

```json
{
  "audio_base64": "…(mp3를 base64로 인코딩)…",
  "alignment": {
    "characters": ["H", "i", " ", "Y", "o"],
    "character_start_times_seconds": [0.0, 0.139, 0.267, 0.325, 0.383],
    "character_end_times_seconds": [0.139, 0.267, 0.325, 0.383, 0.697]
  },
  "normalized_alignment": {}
}
```

공백까지 포함해 글자마다 시작·끝 시각이 온다. 위 예시에서 공백이 0.267~0.325초로 잡힌 것이 실제 단어 사이 간격이고, 마지막 `o`가 0.314초로 긴 것은 문장 끝 모음이 늘어진 결과다.

## 왜 타임스탬프가 정확한가

분석해서 알아낸 값이 아니라 **소리를 만든 쪽이 알려주는 값**이기 때문이다.

TTS는 소리를 만들기 위해 먼저 문장을 발음 단위로 쪼개고, **각 발음이 몇 초 동안 날지 정한 뒤**, 그 설계대로 파형을 생성한다. 즉 타이밍은 합성의 부산물이 아니라 전제다. 그 정보를 응답에 실어주느냐 마느냐의 차이일 뿐이다.

밖에서 오디오를 분석하는 것은 완성된 요리를 먹어보고 레시피를 역추적하는 일이다. 정교해져도 오차가 남는다. 반면 타임스탬프는 레시피를 그대로 건네받는 것이라, **오디오가 애초에 그 설계로 만들어졌으므로 어긋날 수 없다.**

대부분의 TTS도 내부적으로는 같은 정보를 갖고 있다. 다만 "텍스트를 넣으면 오디오가 나온다"는 단순한 규격을 따르느라 응답에 담지 않을 뿐이다.

## 정리

| 방법             | 정확도 | 벤더 교체 | 비고                            |
| ---------------- | ------ | --------- | ------------------------------- |
| 텍스트 균등 배분 | 낮음   | 불필요    | 침묵 구간에 어긋남이 두드러진다 |
| + 음량 그래프    | 중간   | 불필요    | 사전 디코딩이라 iOS 위험 없음   |
| + 주파수 분석    | 중상   | 불필요    | 튜닝 비용이 크다                |
| STT 강제 정렬    | 상     | 불필요    | 왕복 추가로 첫 재생이 느려진다  |
| TTS 타임스탬프   | 최상   | 필요      | 어긋남이 원리적으로 없다        |

정확도 순위는 곧 도입 난이도의 역순이다. 어디까지 갈지는 목표가 가른다.

- **살아있는 대화 상대** — 텍스트 균등 배분으로 충분하다. 입이 말에 맞춰 움직인다는 인상만으로 몰입이 생긴다
- **발음 학습 도구** — 타임스탬프가 전제 조건이다. 다만 그것만으로는 부족하고, 조음 형태를 담은 입모양 그림(f/v의 아랫입술, th의 혀끝 등)이 함께 있어야 한다. 정면 그림으로는 r·l처럼 혀 안쪽 위치로 갈리는 발음을 표현할 수 없다는 한계도 남는다

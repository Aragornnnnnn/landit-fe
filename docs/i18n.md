# 다국어(i18n) 설계

웹 화면을 한국어와 일본어로 보여 준다. 언어는 기기 언어를 따르고 앱 안에서 고르지 않는다. 이 문서는 2026-10-26 기준으로 정한 구조와 이유를 모은다 (LAN-778, 셸 쪽은 LAN-777).

## i18n이 하는 일

i18n(internationalization, 첫 i와 끝 n 사이 18글자)은 코드에 박힌 문구를 걷어내 언어별 파일로 옮기는 작업이다. 화면 코드는 문구 대신 키(`paywall.yearlyStartButton`)를 쓰고, 실행할 때 사용자 언어의 파일에서 그 키의 문구를 꺼낸다. 언어를 하나 늘릴 때 화면 코드는 그대로 두고 파일만 하나 더한다.

문구 말고 같이 바뀌는 것도 있다.

- 숫자·날짜·통화 표기. `₩14,900`과 `¥1,500`처럼 기호 위치와 자릿수가 언어마다 다르다. 직접 이어 붙이지 않고 `Intl` 포매터에 맡긴다.
- 변수가 들어간 문장. 어순이 언어마다 달라 `'월 ' + price`처럼 이어 붙이면 번역이 안 된다. 문장 전체를 키로 두고 변수 자리를 `{price}`로 표시한다(ICU 메시지 형식).

## 글로벌 서비스가 흔히 쓰는 방식

언어를 정하는 방법은 크게 셋이다.

- **URL에 언어를 넣는다** (`/ja/paywall`). 검색 노출이 중요한 웹사이트가 쓴다. 언어마다 페이지를 미리 만들어 둘 수 있다.
- **요청 헤더를 본다** (`Accept-Language`). 브라우저와 WebView가 기기 언어를 자동으로 실어 보내는 표준 헤더다. 앱처럼 URL을 사용자가 보지 않는 서비스가 쓴다.
- **사용자가 고른 값을 저장한다** (쿠키·계정 설정). 앱 안 언어 설정이 있을 때 위 두 방법보다 앞선다.

백엔드에 언어를 알릴 때도 경로(`/ko/api/...`)가 아니라 `Accept-Language` 헤더를 쓰는 게 일반적이다. 언어는 데이터가 아니라 표현 방식이라, 같은 자원의 주소가 언어마다 달라질 이유가 없다.

## 우리 선택

**URL에 언어를 넣지 않고 `Accept-Language`로 정한다.** 랜딧 웹은 WebView 안에서 돌아 검색 노출이 필요 없고, URL에 언어를 넣으면 모든 라우트 폴더를 `[locale]` 아래로 옮겨야 한다. 앱 안 언어 설정이 생기면 그때 쿠키를 판단 순서 맨 앞에 더한다.

**라이브러리는 next-intl.** Next.js App Router에서 가장 많이 쓰이고, 서버 컴포넌트와 클라이언트 컴포넌트를 모두 지원하며, URL 없이 쓰는 방식을 공식 문서로 안내한다. 키를 잘못 쓰면 타입 에러가 나게 할 수 있다. 원문을 키로 쓰고 자동 추출해 주는 Lingui도 검토했지만, 빌드 플러그인이 Next 16·React Compiler 조합에서 도는지 따로 검증해야 해서 보류했다.

## 동작

1. 요청이 오면 서버가 `Accept-Language`에서 지원 언어(ko·ja)를 우선순위 순으로 찾는다. 지역 표기(`ja-JP`의 `-JP`)는 무시한다. 없으면 한국어다 (`shared/i18n/locale.ts`).
2. 정한 언어로 문구 파일을 싣는다. 일본어는 한국어 위에 덮어 합쳐서, 아직 번역 안 된 키는 한국어로 나온다 (`shared/i18n/request.ts`, `messages.ts`). 문구 파일 위치는 아래 "문구 파일 위치와 보내는 양" 절을 본다.
3. 정한 언어를 `<html lang>`에 박는다.
4. 브라우저에서 백엔드로 보내는 요청(`api` 클라이언트)은 `<html lang>`을 읽어 `Accept-Language`로 보낸다. 화면과 API가 같은 값을 쓴다. 백엔드는 지원 헤더 → 저장된 프로필 언어 → `ko` 순서로 언어를 정한다 (landit-be#329).
5. 로그인 상태가 되면 화면 언어를 `PUT /api/v1/me/locale`로 한 번 보낸다 (`shared/i18n/LocaleSync.tsx`). 요청 헤더로는 프로필이 바뀌지 않아서, 푸시·편지처럼 헤더 없는 서버 작업이 쓸 언어를 이걸로 맞춘다. 조회해서 비교해도 요청 수는 같아 비교 없이 매번 보낸다.
6. **일본어 출시 스위치** `NEXT_PUBLIC_JAPANESE_ENABLED`가 `true`일 때만 1~5번이 일본어로 동작한다. 꺼져 있으면 요청 헤더를 읽지 않고 모두 한국어로 보며, 프로필 동기화도 보내지 않는다 (`shared/i18n/japanese-flag.ts`, `resolveRequestLocale`). 문구·백엔드·AI가 갖춰지기 전에 기반 코드를 먼저 배포해도 언어가 섞이지 않게 하려는 장치다.

```tsx
const t = useTranslations('paywall');

<button>{t('yearlyStartButton')}</button>;
```

## 문구 파일 위치와 보내는 양

### 위치

```
src/shared/i18n/
  request.ts, locale.ts, messages.ts   ← 설정 코드
  locales/
    ko.ts   ja.ts                      ← 언어별 묶음 (화면 파일을 모아 내보낸다)
    ko/  common.json  auth.json  paywall.json ...
    ja/  common.json  auth.json  paywall.json ...
```

- **화면 문구는 전부 여기 모은다. 한국어도 코드에서 꺼내 `ko/`로 옮긴다.** 코드에는 키만 남는다. 약관과 서버가 주는 글은 예외다 (키 규칙 7번).
- **언어마다 폴더, 그 안에 화면(네임스페이스)마다 파일 하나.** 새 화면 파일을 만들면 `ko.ts`·`ja.ts`에 한 줄씩 더한다.

근거.

- **FSD 공식 정의.** Shared 레이어의 대표 세그먼트로 `i18n`을 들고 "setup code for translations, global translation strings"라고 설명한다 ([FSD 레이어 문서](https://feature-sliced.design/docs/reference/layers)). 번역 설정과 문구를 같은 `shared/i18n`에 두는 근거다. 슬라이스 안 세그먼트 목록(`ui`·`api`·`model`·`lib`·`config`)에는 번역이 없다 ([FSD 슬라이스·세그먼트 문서](https://feature-sliced.design/docs/reference/slices-segments)).
- **폴더 이름 `locales`는 오픈소스에서 가장 흔하다.** cal.com `packages/i18n/locales/ja/common.json`, Formbricks `apps/web/locales/ja-JP.json`, Excalidraw `packages/excalidraw/locales/ja-JP.json`, Mastodon `app/javascript/mastodon/locales/ja.json`. next-intl 공식 예시는 `messages/`를 쓴다.
- **화면별로 나누는 이유.** 언어당 파일 하나면 cal.com처럼 수천 줄(4,775줄)이 되고, 화면별 PR이 같은 파일에서 충돌한다. next-intl도 파일을 나눠 서버에서 합치는 방식을 공식으로 안내한다 ([next-intl 설정 문서](https://next-intl.dev/docs/usage/configuration)).
- **화면 옆이 아니라 한곳에 모으는 이유.** 번역은 화면이 아니라 언어 단위로 한다. `ja/` 하나를 열어 전체를 봐야 용어를 맞출 수 있고, 계약 테스트·타입도 한 폴더만 보면 된다.

### 브라우저로 보내는 양

서버 컴포넌트(`getTranslations`)가 쓰는 문구는 브라우저로 가지 않는다. 클라이언트 컴포넌트(`useTranslations`)가 쓰는 문구만 `NextIntlClientProvider`가 HTML에 실어 보낸다. 루트에서 전체를 넘기면 앱을 처음 열 때마다 모든 화면의 문구가 실려 간다.

그래서 **화면마다 필요한 묶음만 보낸다.**

```tsx
// app/layout.tsx — 어디서나 쓰는 common만
<RootMessagesProvider>{children}</RootMessagesProvider>

// app/(protected)/paywall/layout.tsx — common에 그 화면 묶음을 더한다
<MessagesProvider namespaces={['paywall']}>{children}</MessagesProvider>
```

화면 layout의 `MessagesProvider`는 바깥 layout이 보낸 묶음 위에 자기 묶음을 더한다(`NestedMessages`). next-intl은 messages를 주면 바깥 것을 갈아 끼우므로 직접 합친다. 그래서 하위 layout은 자기 화면이 새로 쓰는 묶음만 적는다. 루트 layout만 `RootMessagesProvider`로 common을 놓는다.

화면 layout에 네임스페이스를 빠뜨리면 그 화면 문구가 키 그대로(`paywall.title`) 보인다. 테스트는 문구 전체를 채워 주므로 이 실수를 잡지 못한다. 개발 서버 콘솔의 `MISSING_MESSAGE` 에러로 확인한다.

근거. next-intl 문서는 클라이언트에 넘기는 문구를 "Provide the lowest common denominator that contains all messages this component needs to consume"라고 안내한다 ([next-intl 문구 사용법](https://next-intl.dev/docs/usage/translations)). Locize 가이드도 네임스페이스를 나누는 이점으로 그 화면에 필요한 문구만 불러오는 것을 든다 ([Locize 키 네이밍 가이드](https://www.locize.com/blog/guide-to-i18n-key-naming)).

## 키 규칙 (초안, 확정 전)

뼈대는 i18next를 만든 팀(Locize)의 [키 네이밍 가이드](https://www.locize.com/blog/guide-to-i18n-key-naming)다. 그 가이드의 팀 체크리스트 순서대로, 항목마다 우리 결정을 적는다.

### 0. 한눈에 보기

```ts
t('paywall.hero.title'); // 페이월 맨 위 큰 제목
t('paywall.plan.yearlyTitle'); // 플랜 카드의 "연간"
t('paywall.yearlyStartButton'); // 하단 버튼 "7일 무료 체험 시작하기"
t('auth.socialLogin.kakaoButton'); // "카카오로 로그인하기"
t('subscription.manage.cancelButton'); // "구독 해지하기"
```

키는 **어느 화면 → 그 화면의 어느 컴포넌트 → 무슨 일을 하는 글**, 세 칸이다.

### 1. 키는 계약이다

키는 코드와 번역 파일이 서로를 찾는 약속이다. **문구는 언제든 고쳐도 되지만 키 이름을 바꾸면 그 키에 달린 번역이 전부 끊긴다.** ko·ja 파일과 쓰는 코드를 같이 고쳐야 하고, 빠뜨리면 그 자리는 한국어로 대체된다. 그래서 처음에 잘 짓는 게 중요하다.

### 2. 원문이 아니라 의미로 짓는다

```
Good: paywall.yearlyStartButton   → "7일 무료 체험 시작하기"
Bad:  paywall.startSevenDayFreeTrial
Bad:  t('7일 무료 체험 시작하기')   (원문을 키로)
```

안 지키면 — 버튼 문구를 "7일 무료로 시작할게요"로 다듬는 순간 키와 내용이 어긋나고, 1번대로 키를 바꾸면 번역이 끊긴다. 원문을 키로 쓰면 같은 글자인데 번역이 달라야 하는 경우(5번)를 구분할 수도 없다.

### 3. 세 칸 정하는 법

키를 짓다 막히면 그 글이 있는 **파일 경로**를 본다.

**네임스페이스 = 어느 화면(도메인)에 있나.** 라우트·도메인 폴더 이름을 쓴다. 문구 파일 이름도 같다.

```
app/(protected)/paywall/          → paywall        (locales/ko/paywall.json)
app/(public)/(auth)/              → auth
app/(protected)/me/subscription/  → subscription
features/conversation/            → conversation
```

**자리 = 그 화면의 어느 컴포넌트에 있나.** 글이 들어 있는 컴포넌트 이름을 쓴다. 화면 전체에 걸친 글(하단 고정 버튼 등)이면 생략한다.

```
paywall/_ui/PaywallHero.tsx                  → hero
paywall/_ui/PlanSection.tsx                  → plan
(auth)/_ui/SocialLoginButtons.tsx            → socialLogin
subscription/_ui/SubscriptionManageScreen.tsx → manage
```

**역할 = 그 글이 화면에서 무슨 일을 하나.** 마지막 칸을 아래 단어로 끝낸다. 구분이 필요하면 앞에 붙인다 (`yearlyStartButton`, `failedError`). 목록에 없는 역할이 생기면 목록부터 늘린다.

```
title        큰 제목               button       버튼 글자
subtitle     제목 밑 부제          link         글 속 링크 글자
description  설명 문단             label        선택지·항목 이름, 화면에 안 보이는 접근성 이름
body         긴 본문               placeholder  입력칸 안내
caption      버튼·카드 밑 작은 글   hint         입력칸 밑 도움말
badge        작은 딱지             error        에러 문구
toast        잠깐 뜨는 알림
```

가이드 예시에는 가운데 칸에 요소 종류를 두는 방식(`checkout.buttons.confirmOrder`)도 있다. 우리는 컴포넌트를 두고 역할을 끝에 붙이는 방식(`checkout.paymentForm.submitButton`)을 쓴다. 문구를 컴포넌트 파일 기준으로 찾을 수 있기 때문이다.

### 4. 표기와 깊이

- **camelCase 영어, 점으로 구분.** 가이드는 "하나로 정해 통일하라"고만 한다. TS 코드 안에서 키와 변수(`{price}`)가 같은 표기가 되도록 camelCase로 정했다.
- **네임스페이스 포함 최대 3단계.** 가이드 권장(2~3단계)과 같다. 더 깊어지면 찾고 옮기기 어렵다.

### 5. 재사용은 기본 금지, common은 엄격하게

**쓰는 자리마다 고유 키를 둔다.** 한국어가 같아도 따로 둔다.

```
subscription.manage.cancelButton           "구독 해지하기"   → ja 解約する
subscription.manage.undoCancelButton       "해지 취소하기"   → ja 解約を取り消す
conversation.transcriptEditor.cancelButton "입력 취소"     → ja 入力をキャンセル
Bad: common.cancel 하나로 셋 다
```

안 지키면 — 가이드의 예시 그대로다. "Cancel"이 구독 해지와 다이얼로그 취소로 갈리듯, 우리 "취소·해지"도 일본어에서 解約·取り消し·キャンセル로 갈린다. 키 하나로 묶으면 하나밖에 못 고르고, 한국어에서도 한 자리만 바꾸려 해도 전부 같이 바뀐다.

**common에는 어느 화면에서든 같이 바뀌어야 하는 것만 둔다.** 새로 넣을 땐 "한 곳을 바꾸면 나머지도 반드시 같이 바뀌어야 하는가"를 묻는다. 지금 후보는 이 정도다.

```
common.closeLabel     모달 X 버튼의 접근성 이름 "닫기"
common.retryButton    네트워크 실패 화면의 "다시 시도"
요일·언어 이름처럼 뜻이 고정된 말
```

### 6. 문장·변수·링크

**문장은 쪼개지 않는다. 변수와 링크는 문장 안에 둔다.**

```
Good: "yearlyBillingCaption": "7일 무료 체험 후 연 {price} 정기 결제 · 언제든 해지 가능"
      "termsCaption": "<link>이용약관</link>에 동의해요"
Bad:  "billingPrefix": "7일 무료 체험 후 연", "billingSuffix": "정기 결제"
```

안 지키면 — 코드가 "앞 조각 + 가격 + 뒤 조각" 순서로 붙이게 되는데, 일본어는 가격이 들어가는 위치가 달라 조각을 아무리 잘 번역해도 문장이 안 된다. 링크·강조는 HTML을 넣지 않고 태그로 표시해 `t.rich`로 컴포넌트를 끼운다 (가이드도 같은 방식을 권한다).

**줄바꿈은 문장 안에 `<br></br>`로 둔다.** 화면은 `t.rich('key', lineBreak)`(`shared/i18n/rich.tsx`)로 그린다. `<br/>`처럼 스스로 닫는 태그는 next-intl이 글자 그대로 내보내서 계약 테스트가 막는다. 줄을 바꾸는 자리와 횟수는 언어마다 달라도 된다(일본어는 낱말 중간에서도 줄이 넘어가 더 자주 끊는다).

안 지키면 — 두 줄 제목을 키 두 개로 쪼개게 되는데, 일본어는 줄이 끊기는 자리가 달라 한 문장으로 번역할 수 없다.

**경우가 갈리면 문장마다 키를 따로 둔다.**

```
지금 코드 (paywall-copy.ts)
  plan.id === 'yearly' ? '7일 무료 체험 시작하기' : `월 ${formatWon(plan.price)}으로 시작하기`

Good: "yearlyStartButton": "7일 무료 체험 시작하기"
      "monthlyStartButton": "월 {price}으로 시작하기"
Bad:  "startButton": "{plan, select, yearly {7일 무료 체험 시작하기} other {월 {price}으로 시작하기}}"
```

안 지키면 — 두 문장이 문법 기호 사이에 끼어 한 줄이 된다. 번역하다 괄호 하나만 빠져도 그 키를 쓰는 화면이 에러가 나고, 월간 문구만 고치려 해도 연간 문장까지 열어야 한다. 개수에 따라 말이 바뀌는 복수형처럼 문장 안에서만 갈리는 건 ICU로 한 키에 둔다.

**키에 순번을 넣지 않는다.**

```
Good: onboarding.widget.title
Bad:  onboarding.step3.title
```

안 지키면 — 온보딩에 위젯 안내 스텝이 끼어들었던 것처럼 순서가 바뀌면 `step3`이 다른 화면을 가리킨다. 키를 바꾸면 1번대로 번역이 끊긴다.

### 7. 글 종류별로 두는 곳

- **화면 문구**(제목·버튼·안내)는 JSON 키에 둔다. 긴 안내문도 문단 하나당 키 하나다.
- **약관·개인정보처리방침**은 같은 타입(`LegalDocument`)의 언어별 문서 파일로 둔다 (`terms/document.ko.ts`, `document.ja.ts`). 언어마다 시행일·버전이 따로 갈 수 있어 키로 쪼개지 않는다.
- **콘텐츠 데이터**(페이월 데모의 give it a shot 예문 등)는 구조·영어·그림을 코드에 두고, 해석만 키로 둔다.
- **서버가 주는 글**(시나리오 대사·AI 피드백·편지 본문)은 이 구조 밖이다. 백엔드가 언어별로 내려준다.
- **한국어 화면에만 나오는 문구**(환급·이용권·한국 스토어 리뷰처럼 일본어 화면에서 꺼지는 것)는 옮기지 않고 코드에 한국어로 둔다. 자리마다 "한국어 화면에만 있어 옮기지 않는다" 주석을 단다.
- **모델이 문구를 고를 때** 변수가 없으면 키를 돌려주고(`LEVEL_NAME_KEYS`), 가격처럼 변수가 들어가면 번역 함수(`Translator<'paywall'>`, `shared/i18n/translator`)를 받아 문장을 돌려준다.

### 8. 관리

- 없는 키를 코드에서 쓰면 타입 에러가 난다.
- 계약 테스트(`shared/i18n/locales.test.ts`)가 막는 것 — 키 표기(camelCase·순번 없음·3단계 이하), 역할 단어로 끝나는지, 빈 문구, 언어끼리 다른 네임스페이스, 일본어 파일에만 있는 키, 언어끼리 다른 변수(`{price}`)·태그(`<link>`). 역할 단어를 늘릴 땐 테스트의 `ROLES`와 위 목록을 같이 늘린다.
- 안 쓰는 키는 CI에서 걸러낸다 (가이드 권장). 문구를 어느 정도 옮긴 뒤에 더한다.
- 키 이름을 바꿀 땐 ko·ja 파일과 쓰는 코드를 한 커밋에서 같이 바꾼다.
- 여러 화면이 같이 쓰는 컴포넌트(`features/conversation` 등)의 문구는 feature 이름 네임스페이스(`conversation`)에 두고, 그 컴포넌트를 쓰는 화면 layout이 그 묶음을 같이 보낸다.

### 테스트

`vitest.setup.ts`가 `useTranslations`를 실제 한국어 파일로 채운다. Provider 없이 렌더해도 화면에 예전과 같은 한국어가 그려져서, 문구를 키로 옮겨도 `getByText('구독 해지하기')` 같은 기존 테스트가 그대로 통과한다. 첫 예시로 모달 닫기 버튼(`common.closeLabel`)을 옮겼고 기존 모달 테스트는 고치지 않았다.

일본어는 화면마다 테스트하지 않는다. 문구 파일은 계약 테스트가 보고, 언어에 따라 동작이 갈리는 곳(일본어에서 카카오 로그인 숨김 등)만 일본어로 렌더해 확인한다. 렌더하기 전에 `setTestLocale('ja')`(`shared/i18n/test-locale.ts`)를 부르면 그 테스트만 문구·`useLocale`·`<html lang>`이 일본어가 된다. 테스트가 끝나면 한국어로 돌아간다.

```tsx
it('일본어 화면에서는 카카오 로그인을 숨긴다', () => {
  setTestLocale('ja');

  render(<SocialLoginButtons />);

  expect(
    screen.queryByRole('button', { name: /카카오/ }),
  ).not.toBeInTheDocument();
});
```

테스트 설정은 `useTranslations`·`useFormatter`·`useLocale`·`useMessages`·`useTimeZone`·`useNow`를 채운다. 다른 next-intl 훅을 쓰게 되면 여기에 더한다.

## 일본어 화면에서 꺼지는 기능

일본은 구독(월간·연간)만 판다. 환급·친구 초대·할인은 한국 전용이라 일본어 화면에서는 보이지 않는다. 기준은 화면 언어 하나다. 일본에 사는 사람이라도 기기가 한국어면 한국어 화면을 본다.

| 기능             | 끄는 자리                            | 함께 빠지는 것                                                                                                                                 |
| ---------------- | ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| 환급 챌린지      | `isRewardChallengeLive`(언어 조건)   | 환급 화면(들어오면 홈으로), 헤더 적립 금액·동전 연출, 페이월의 환급 혜택·이용권 결제, 내 정보 환급 타일, 해지 흐름의 환급액, 결제 후 환급 문구 |
| 친구 초대        | 환급을 따른다(`useReferralAudience`) | 초대 화면(들어오면 내 정보로), 배너, 초대 안내 편지 버튼                                                                                       |
| 온보딩 초대 코드 | `canEnterReferralStep`(언어 조건)    | 초대 코드 단계                                                                                                                                 |
| 페이월 이탈 할인 | `usePromoLive`                       | 닫을 때 서버에 알리기, 헤더 할인 배지                                                                                                          |
| 튜토리얼 프리뷰  | 꺼지지 않는다(`usePremiumPreview`)   | 적립 문장 두 개 대신 "매일 시나리오 하나씩" 문장으로 소개                                                                                      |
| 스토어 평점·리뷰 | `showsStoreReviews`                  | 페이월 혜택 화면의 평점과 리뷰 카드(한국 스토어 글이고, 일본 스토어엔 아직 평점이 없다)                                                        |

한국 전용 상품의 언어 조건은 `sellsKoreaOnlyOffers`(shared/i18n/locale)다. 새 화면이 환급·초대 금액을 보여 주면 이 판정을 따라야 한다. 스토어 리뷰(`showsStoreReviews`)는 본문이 같아도 따로 둔다. 일본 스토어에 평점이 생기면 이것만 풀린다. 이미 환급에 참여한 사람이 기기 언어를 일본어로 바꿔도 환급 화면은 숨긴다(드문 경우라 언어 기준을 그대로 따르기로 했다). 개발자 묶음의 프리뷰 다시 보기는 일본어 화면에서도 환급 진입을 보여 준다(개발 전용). 서버가 내용을 정하는 홈 이벤트 공지와 편지, 약관의 환급·초대 조항은 코드로 막을 수 없어서, 운영에서 일본어 사용자에게 보내지 않는다.

## 바뀌는 것과 주의할 것

- **스위치를 켜면 정적 페이지가 없어진다.** 헤더를 읽는 순간 모든 페이지가 요청마다 서버 렌더가 된다(develop 기준 정적 29개). 꺼져 있는 동안은 헤더를 읽지 않아 정적 그대로다(빌드로 확인). 문서 응답은 이미 `no-store`라 캐시 손실은 없고, 켠 뒤 늘어나는 건 서버 렌더 시간이다. 켠 뒤 첫 응답 시간을 확인한다.
- **iOS WebView의 `Accept-Language`는 앱이 선언한 지원 언어를 따르는 것으로 알려져 있다.** 셸에 일본어를 선언하기 전(LAN-777 전)에는 일본어 기기에서도 한국어로 보일 수 있다. 시뮬레이터로 확인이 필요하다.
- **서버가 먼저 보내는 문구**(푸시·편지)는 요청 헤더가 없다. 백엔드가 프로필 언어를 쓰고, 프론트가 로그인 때마다 PUT으로 맞춘다.
- **스위치를 켜는 순서.** `PUT /api/v1/me/locale`은 landit-be#329가 배포돼야 생긴다. 스위치를 꺼 둔 동안은 이 요청을 보내지 않아 웹을 먼저 배포해도 된다. 켜기 전에 백엔드 배포를 확인한다. 켠 채로 백엔드가 없으면 앱을 켤 때마다 404가 Sentry 경고로 쌓인다.
- **켰다가 다시 끌 때.** 끈다고 이미 `ja`로 저장된 프로필이 `ko`로 돌아가지는 않는다. 그 사이 동기화된 사용자는 화면이 한국어인데 푸시·편지는 일본어로 받을 수 있어서, 되돌릴 땐 백엔드에서 프로필 언어를 `ko`로 되돌린다.
- **api 클라이언트를 거치지 않는 요청**(소셜 로그인·토큰 재발급)에는 언어 헤더가 없다. 백엔드는 이때 프로필 언어로 응답한다. 이 요청들의 문구는 화면에 그대로 쓰지 않아 지금은 두었다.
- 위젯·알람처럼 네이티브가 그리는 문구는 이 구조 밖이다.

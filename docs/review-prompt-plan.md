# 스토어 리뷰 더 받기 — 계획과 근거

작성 2026-10-16. 숫자는 iOS 앱 유저, 최근 90일(7/18~10/16). 앱 유저의 97%가 iOS라 iOS만 본다.

## 한 줄

「좋았어요」 한 사람에게 **뭔가 마치고 홈에 올 때마다 하루 한 번** 리뷰를 묻고(최대 4번), 버튼을 누르면 **앱 안에서 별점 카드**를 띄운다.

## 지금

1. 대화 끝나고 홈 → "방금 대화 어떠셨나요?" → 「좋았어요」. 평생 1번.
2. 「좋았어요」 한 사람이 **다른 날** 돌아와 대화를 마치면 → "응원 남겨주세요" 시트. 평생 1번. 닫으면 끝.
3. 버튼을 누르면 앱스토어 앱으로 나가서 거기서 별점·리뷰.

```
「좋았어요」        1,190명
  └ 리뷰 시트 봄      498명  (42%)   ← 58%는 다른 날 안 돌아와서 영영 못 본다
      └ 버튼 누름      190명  (38%)   ← 닫은 308명은 영영 끝
          └ 별점      ≤44개  (23%↓)  ← 출시 후 누적. 스토어 앱에서 또 눌러야 해서 제일 많이 샌다
```

## 바꾼 뒤

### 유저가 보는 흐름

1. 대화 끝나고 홈 → 「좋았어요」. (지금과 같음)
2. 그 다음부터 **대화든 표현 학습이든 마치고 홈에 오면** 리뷰 시트. 같은 날이어도 뜸. 하루 1번.
3. 시트에서
   - 「리뷰 남기러 가기」 → **앱 안에 iOS 별점 카드.** 별 한 번이면 끝. 카드가 0.5초 안에 안 뜨면 지금처럼 앱스토어로. 스토어로 간 건 끝이 아니다 — 간 사람 4명 중 3명이 안 쓰고 돌아오니 닫은 것과 같이 2일 뒤 다시 묻는다.
   - X 또는 닫기 → 쉬었다가 다시. 닫은 날부터 **2일 → 4일 → 6일** 뒤부터 다시 뜰 수 있음. 재요청 3번까지(총 4번).
   - 「이미 남겼어요」(재요청부터 보이는 작은 링크) → 영구 끝.

### 간격 규칙

- 2·4·6은 "최소 이만큼 쉰다"다. 닫고 6일 뒤에 와도 1차 재요청이 뜬다. 건너뛰지 않는다.
- 세는 건 "몇 번째 재요청인가", 간격은 "마지막으로 닫은 날부터 며칠 지났나".
- 날짜 기준이지 대화 횟수 기준이 아니다. 하루에 여러 판 하는 사람이 이틀 만에 4번 다 보지 않게.

예 — 1일 닫음 → 7일 옴 → 1차 → 닫음 → 9일 옴(4일 안 됨, 안 뜸) → 12일 옴 → 2차 → 닫음 → 20일 옴 → 3차 → 닫음 → 끝.

## 근거

### 왜 같은 날에도 묻나

- 「좋았어요」 한 사람의 **58%는 다른 날 안 돌아온다.** 지금 규칙으론 영영 못 묻는다.
- 「좋았어요」 하고 **12시간 안에 시나리오를 하나 더 마치는 사람이 13%(160명)**, 중앙값 10분 뒤. 지금은 이들에게 아무것도 안 묻는다.
- 가설 — 이 160명이 지금 시트 전환(38%)만큼 누르면 **+60명.**

### 왜 표현 학습 뒤에도 묻나

- 후보 순간별 유저 수(90일). 대화 완료 1,615 · **표현 학습 완료 899** · 레벨 결과 971(첫날 1번뿐) · 푸시 복습 897(홈 안 옴) · 스트릭 536(조회 화면) · 발음 결과 434(대화 도중) · 위젯 설치 248 · 결제 138.
- 표현 학습은 대화 안 한 날에도 생기는 성공 순간이고 홈으로 돌아온다. 나머지는 수가 작거나 끊기 나쁜 자리다.

### 왜 2·4·6일, 왜 4번까지

- 리뷰 시트를 **닫은 303명**이 닫고 N일 뒤에도 다시 대화하는 비율.

| N일 뒤 | 2   | 4   | 6   | 12  | 14  | 30  |
| ------ | --- | --- | --- | --- | --- | --- |
| 비율   | 51% | 42% | 38% | 27% | 25% | 12% |

- 1차(2일째) ~155명, 2차(6일째) ~115명, 3차(12일째) ~80명에게 닿는다. 합쳐 ~350번 노출, 15%만 눌러도 **+50명.**
- 4차를 넣으면 30일째라 ~35명에게 닿고 누르는 사람 5명 정도. 짜증 대비 남는 게 없어 3번에서 끊는다.
- 2일 vs 3일은 닿는 수(51% vs 46%) 기준이고, 짜증 차이는 데이터가 없다. 배포 뒤 재요청 노출의 「아쉬웠어요」·삭제율로 본다.

### 왜 앱 안 카드인가

- 버튼 누른 190명 중 별점은 많아야 44개(23%). **가장 큰 구멍.**
- 카드는 iOS가 **기기당 1년 3번**만 띄워 주고 떴는지 알려주지 않는다. 그래서 버튼을 누른 사람에게만 쓰고, 안 뜨면(0.5초 감지) 바로 지금처럼 스토어로 보낸다. 누른 직후라 폴백이 어색하지 않다.
- 가설 — 누른 사람 중 별점 23% → **60% 안팎**(추정). 스토어 앱 이탈이 사라진다.

### 왜 「이미 남겼어요」를 두나

- 끝은 「이미 남겼어요」와 4번 소진, 둘뿐이다. 스토어로 갔다고 끝내면 안 쓰고 돌아온 4명 중 3명을 다시 못 묻는다. 정말 쓴 사람은 이 링크로 끝낸다. 재설치한 사람도 같다.

## 합치면 (90일, 가설)

```
              지금        바꾼 뒤
리뷰 노출      498   →   498 + 160(같은 날) + 350(재요청) ≈ 1,000
버튼 누름      190   →   190 + 60 + 50 ≈ 300
별점          ≤44   →   300 × 60% ≈ 180   (카드 안 뜨는 사람은 지금처럼 23%)
```

효과의 대부분은 카드다. 시점·재요청은 그 카드를 더 많은 사람에게 보여주는 역할.

## 가설과 목표 — 배포 뒤 무엇을 보나

기준선은 iOS 90일(7/18~10/16). 비교는 배포 뒤 같은 길이로 하되, 2주 지나면 먼저 본다.

| 지표                        | 지금 (90일) | 1단계 뒤 목표 | 2단계 뒤 목표 |
| --------------------------- | ----------- | ------------- | ------------- |
| 리뷰 시트 노출              | 498         | ~1,000 (2배)  | 같음          |
| 버튼 누름                   | 190         | ~300          | 같음          |
| 누른 사람 중 별점 비율      | ≤23%        | 같음          | 60% 안팎      |
| 앱스토어 별점 (누적 증가분) | 44          | ~70 (+25)     | ~180          |

가설 셋. 각각 계측 속성 하나로 바로 확인된다.

1. **같은 날 2회차에도 지금만큼 누른다** — `trigger`별·`attempt=1` 중 같은 날 노출의 누름 비율이 30% 이상이면 맞다. 15% 밑이면 같은 날은 뺀다.
2. **재요청도 누른다** — `attempt` 2·3·4의 누름 비율이 15% 안팎이면 맞다. 10% 밑으로 떨어지는 attempt부터 끊는다(4 → 3).
3. **앱 안 카드는 스토어 이동보다 훨씬 많이 별점으로 이어진다** — 2단계 배포 뒤 주간 별점 증가분이 버튼 누름의 절반 이상이면 맞다. (카드는 떴는지만 알고 별점을 남겼는지는 모르니 스토어 콘솔 수로 본다.)

나빠지는 신호. 재요청 노출이 있는 주에 「아쉬웠어요」 비율이나 삭제가 눈에 띄게 늘면 간격을 벌린다(2·4·6 → 3·6·9). 상수 두 개라 한 줄이다.

## 순서

1. **웹만, 바로** — 시점(같은 날·표현 학습)·재요청(2·4·6, 4번)·X·「이미 남겼어요」·계측. 2주 뒤 노출·버튼 수 변화 확인.
2. **앱 업데이트** — 카드. 브릿지 + 셸 + iOS 로컬 모듈 + 심사. 별점 수 주간 추이로 검증.
3. **후속** — 카드가 안정적이면 시트 없이 조건 충족 시 조용히 카드만 띄우는 그룹을 비교.

## 계측 (1단계에 같이)

- `platform` 유저 속성.
- 리뷰 시트 노출에 `trigger`(`talk` / `expression`), `attempt`(1~4).
- 버튼 결과 `method`(`card` / `store`), 카드 `shown` / `not_shown`.
- 시트 답에 `already_done`.
- 최종 지표는 앱스토어 별점 수. landit-alerts에 주간 집계 한 줄.

## 부록 — 카드 연결 방법

```
웹(시트 버튼 탭)
  │ bridgeVersion >= 9
  ├─ { type: 'REQUEST_REVIEW' } ───────────────▶ 셸
  │                                               로컬 모듈 requestReview()
  │                                               iOS: AppStore.requestReview → 0.5초간 카드 창 감시
  │                                               Android: Play ReviewManager(왕복 2초 마감) → 카드 단계가 1초 안에 끝나는지
  │ ◀──── { type: 'REVIEW_RESULT', status } ──────┘
  ├─ shown                → 시트 닫고 끝
  ├─ not_shown/unavailable/3.5초 무응답 → 스토어 딥링크 (지금 동작)
  │ bridgeVersion < 9 · 브라우저
  └─ 앱스토어 딥링크
```

- `packages/bridge/src/messages.ts` — `REQUEST_REVIEW`, `REVIEW_RESULT { status: 'shown' | 'not_shown' | 'unavailable' }`, `NATIVE_BRIDGE_VERSION` 8 → 9. `GET_OFFERINGS ↔ OFFERINGS` 꼴.
- 셸 — 로컬 모듈 `modules/review-prompt` 하나가 iOS·Android를 다 맡는다. Play 스토어가 없으면 `unavailable`. 연타 잠금은 `share.ts`처럼.
- iOS 로컬 모듈(위젯 설치 감지용) — `UIWindow.didBecomeVisibleNotification` 구독, 클래스 이름 `SKStoreReviewPresentationWindow`면 `shown`, 0.5초 안에 없으면 `not_shown`(실측 40ms에 뜸). 공개 API만 쓴다.
- 웹 — `SatisfactionGate.tsx`의 `writeReview`에서 분기. 기록은 `prompt-record.ts`의 `ImpressionRecord`에 `attempt` · `lastClosedOn` · `done`.
- Android — Play `ReviewManager`로 카드를 띄운다. Play 서버 왕복(`requestReviewFlow`)이 끝난 뒤 카드 단계(`launchReviewFlow`)만 재서, 1초 안에 끝나면 `not_shown`(실측 81~545ms), 1초가 지나도록 안 끝나면 그 자리에서 `shown`. 카드가 닫히길 기다리지 않는다 — 기다리면 웹이 먼저 포기해 카드 위에 스토어가 열린다.
- 규정 — iOS 심사 지침은 "커스텀 프롬프트 대신 제공 API". StoreKit 문서는 "안 뜰 수 있으니 버튼에 묶지 말라"고 권하는데 우리는 안 뜨면 스토어로 보낸다. 반려 사례는 모른다(추정). Android 가이드의 "카드 전 질문 금지"는 소감 시트가 리뷰와 분리된 제품 피드백이라 해당 없다고 봄(추정).
- 후순위 — 리뷰 기록 서버 보관(재설치 초기화 방지).

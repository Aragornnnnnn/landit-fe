# PR 올리기

## 먼저 확인할 것

PR을 만들기 전에 세 가지를 본다. 순서대로.

1. **브랜치와 경로.** 워크트리가 여럿이다. `git worktree list`로 올릴 브랜치가 어느 폴더에 있는지 먼저 찾고, 그 폴더에서 `git branch --show-current`가 `feat/LAN-XX` 같은 이슈 번호 브랜치인지 본다. `main`·`develop`이면 멈춘다. 머지 직후나 인터럽트 뒤 턴에는 로컬이 develop으로 바뀌어 있는 일이 실제로 있었다. 검사와 생성은 전부 그 폴더에서 한다.
2. **검사.** 루트에서 CI와 같은 순서로 `pnpm format:check` → `pnpm lint` → `pnpm typecheck` → `pnpm test` → `pnpm build`. 문서만 바꾼 PR이면 `build`는 건너뛰어도 되지만 나머지는 돌린다. `--filter web`만 돌리면 `packages/analytics`의 이벤트 이름 컨벤션 테스트를 건너뛰어 CI가 빨간불로 올라간다. 새로 판 워크트리에 `node_modules`가 없으면 커밋 훅(husky의 prettier)이 조용히 안 돌아 포맷이 안 맞은 채 커밋된다. 워크트리를 만들었으면 `pnpm install`부터. 문서만 바꾼 PR도 포맷 검사는 받는다.
3. **승인.** "이 브랜치 PR 올릴까요?"를 **이 PR에 대해** 묻는다. 앞선 PR의 승인, 스택 흐름, "빨리 가자" 분위기는 다음 PR의 승인이 아니다. 사용자가 코드를 아직 못 본 변경이면 더더욱. 급하면 Draft를 제안한다.

세 번째는 건너뛸 수 없다. 사용자 확인 없이 올렸다가 되돌린 전례가 있고, 수습은 `gh pr ready --undo`(Draft 전환) → 필요하면 close다.

## 제목

노션 이슈 제목 그대로. 이슈 번호는 제목에 넣지 않는다(브랜치명과 본문 "관련 이슈"에 있다). 이슈 제목을 모르면 사용자에게 묻는다. 지어내지 않는다.

릴리즈 PR(develop → main)은 이 스킬이 아니라 `release` 스킬을 쓴다.

## 본문

`.github/PULL_REQUEST_TEMPLATE.md`의 네 섹션을 그 순서 그대로 쓴다. 자유 형식으로 올렸다가 "템플릿 왜 안 지키는데"라고 지적받았다. 섹션을 빼거나 이름을 바꾸지 않는다. 해당 없는 섹션은 "해당 없음"이라고 적는다.

```
## 관련 이슈

LAN-XX

## 무엇을, 왜

{제3자가 봐도 이해되게. 아래 문체 규칙}

## 리뷰 포인트

{리뷰어가 집중해서 봐 줬으면 하는 부분. 판단이 갈리는 결정과 그 근거}

## 체크리스트

- [x] 코드 추가 500줄 이하 (5~10분 리뷰 가능한 볼륨)
- [x] 브랜치 이름에 이슈 번호 포함 (`feat/LAN-XX`)
- [x] 커밋 메시지가 컨벤션(`{type}({scope}): 메시지`)을 따름
```

체크리스트는 실제로 확인한 것만 체크한다. 500줄을 넘으면 체크하지 말고 "무엇을, 왜"에 왜 나누지 않았는지 한 줄 적는다.

### 문체

팀에 공개되는 문서다. 백엔드 등 프론트 아닌 팀원도 읽는다.

- **의도 프레이밍으로 쓴다.** "X가 없었다", "Y가 안 됐다", "빠져 있었다"로 시작하지 않는다. 같은 사실을 "무엇을 할 수 있게 하려고 무엇을 더한다"로 적는다. 새 기능이 버그처럼 읽히거나 누군가의 잘못처럼 보이면 안 된다. 문장 단위로도 같다 — "안 실렸다"가 아니라 "실어 주었다", "없어서 못 했다"가 아니라 "대신 이렇게 하도록 했다". 리뷰 포인트와 근거 문장까지 전부.
- **사실 서술로 짧게.** "~이 이번 구현의 핵심입니다", "증상의 핵심은" 같은 강조·연출 문구를 쓰지 않는다. 볼드 남발 금지. 불릿은 "사실 — 이유" 구조.
- **불릿 사이에 빈 줄을 둔다.** 한 항목이 두 줄을 넘는 목록은 빈 줄 없이 붙이면 GitHub에서 한 덩어리로 뭉쳐 읽기 어렵다. 체크리스트처럼 한 줄짜리 항목만 붙여 쓴다.
- **전문용어는 풀어 쓴다.** User-Agent가 아니라 "접속한 기기가 아이폰이면". 프론트 사전지식 없이 읽혀야 한다.
- **버그 수정은 원인 / 확인 / 해결 세 항목**으로. 원인 항목은 문제를 그대로 적어도 된다(사실이니까). 단 "누가 빠뜨렸다"가 아니라 "어떤 조건에서 어떻게 됐다"로.
- **쓰고 나서 한 번 검색한다.** "없었다", "안 됐다", "못 했다", "빠져", "문제였다"가 본문에 남아 있으면 같은 사실을 더해 준 것으로 바꿔 적는다. 초안에는 거의 항상 남아 있다.

### 이해를 돕는 이미지 한 장

글로만 설명하면 리뷰어가 코드를 열어야 그림이 그려진다. 이미지 한 장을 "무엇을, 왜" 아래에 넣는다. 종류는 변경이 정한다.

- **화면이 바뀌면 캡처.** 전후가 있으면 전/후 두 장을 나란히. 찍는 방법은 `capture` 스킬을 따른다.
- **구조·흐름이 바뀌면 도식.** 상태 전이, 데이터 흐름, 브릿지 메시지 순서 같은 것. 화면은 그대로인데 값이 여러 파일을 거쳐 흐르게 된 변경(예: 페이월 진입 문 → 주소의 `source` → 페이지뷰 속성)도 여기다. 리뷰어가 파일 넷을 열어야 그림이 그려지면 도식이 필요한 것이다. HTML이나 SVG로 그려 PNG로 찍는다(`capture` 스킬). 상자와 화살표면 충분하다. 꾸미지 않는다.
- **둘 다 아니면 넣지 않는다.** 이름 바꾸기, 설정 변경, 문서 수정에 이미지를 억지로 만들지 않는다.
- **화면이 여러 장이면 썸네일 표 대신 흐름도 한 장.** ① → 사유별 ② → ③처럼 갈림길이 있는 흐름은 캡처를 따로 늘어놓으면 순서가 안 읽힌다. 캡처 전부를 한 HTML에 행(갈림길)·열(다음 화면)로 배치하고 라벨·화살표를 붙여 PNG 한 장으로 찍는다(`capture` 스킬의 도식 방법). 개별 캡처는 pr-assets 폴더에 같이 두고 본문에는 흐름도만 넣는다. 본문에 관련 피그마 섹션 링크도 함께 적는다.

이미지는 작업 브랜치에 커밋하지 않는다. `docs/images` 같은 곳에 넣었다가 옮긴 전례가 있다. **`pr-assets` 브랜치의 `lanXXX/` 폴더**에 올리고 raw 링크로 넣는다.

```bash
# 로컬 워크트리가 있으면 그걸 쓴다 (../landit-fe-pr-assets, 브랜치 pr-assets)
cd ../landit-fe-pr-assets && git pull -q
mkdir -p lanXXX && cp /경로/이미지.png lanXXX/
git add lanXXX && git commit -m "chore: LAN-XX PR 이미지 추가" && git push
```

워크트리가 없으면 `gh api -X PUT repos/Aragornnnnnn/landit-fe/contents/lanXXX/파일.png -f branch=pr-assets -f message="..." -f content="$(base64 -i 파일.png)"`로 올린다.

본문에는 이렇게 넣는다.

```html
<img
  width="180"
  src="https://raw.githubusercontent.com/Aragornnnnnn/landit-fe/pr-assets/lanXXX/파일.png"
/>
```

여러 장이면 `<img width="180">`을 표 셀에 넣어 4열·3열로 배치한다(#183 참고). **푸시하기 전에 raw URL을 curl로 확인하지 마라.** GitHub CDN이 404를 약 5분 캐시해 PR에서 깨져 보인다. 확인은 푸시 뒤에만.

## 라벨

타입 하나 + 범위 하나 이상. 이름에 이모지와 `#`가 포함돼 있으니 그대로 쓴다.

- 타입 — `feat ✨` `fix 🐛` `refactor ♻️` `docs 📝` `chore 🔧` `remove 🗑️` `test ✅`. 커밋 타입이 섞여 있으면 **변경의 목적이 되는 커밋의 타입** 하나만 붙인다(기능을 더하려고 타입·테스트·문서를 같이 고쳤으면 `feat ✨`). `design` 라벨은 없으니 UI 변경은 `feat ✨`나 `fix 🐛` 중 가까운 쪽.
- 범위 — `#web` `#mobile` `#common`(루트·packages).
- 특수 — `hotfix 🔥` `ci ⚙️` `deps 📦` `poc 🧪`(머지 안 하는 실험).

## 만들기

승인을 받은 뒤에만.

```bash
gh pr create --base develop --assignee @me --title "{노션 이슈 제목}" --label "feat ✨" --label "#web" --body-file /tmp/pr-body.md
```

`--assignee @me`는 빼지 않는다. PR 작성자를 어사이니로 넣는 것이 팀 규칙이다. 본문은 파일로 넘긴다. 인라인 문자열은 따옴표와 줄바꿈에서 깨진다. Draft면 `--draft`. 스택 PR이면 `--base`를 앞 PR의 브랜치로.

만든 뒤 URL을 사용자에게 주고, 노션 이슈 체크박스는 머지 뒤 사람이 닫는다는 것을 기억한다(에이전트가 닫지 않는다).

## 하지 않는 것

- 커밋 메시지에 `Co-Authored-By: Claude` 트레일러를 넣지 않는다. 이 레포는 히스토리 재작성까지 해서 지웠다.
- PR 브랜치에 후속 커밋을 밀기 전에 `gh pr view N --json state`부터 본다. 머지된 PR은 `mergeable`이 UNKNOWN으로 굳는다. 지연이 아니라 닫힌 것이다.
- 체크리스트·컨텍스트 노트 파일은 커밋하지 않는다.

# 테스트

## 언제 쓰나

**시키지 않아도.** AGENTS.md가 "구현은 TDD로 — 시키지 않아도 기본값이 TDD다"라고 정해 뒀다. 테스트 없이 로직만 쓰고 넘어갔다가 지적받은 전례가 있다. 새 로직, 버그 수정, 갈림길이 생기는 변경은 테스트를 먼저 쓴다.

브랜치를 전환했으면(특히 develop에서 새로 팔 때) `AGENTS.md`와 `docs/testing.md`를 다시 읽는다. 세션 시작 시 읽은 것이 옛 브랜치 스냅샷일 수 있다.

규칙 원문은 `docs/testing.md`다. 여기는 그걸 절차로 풀어 둔 것이고, 둘이 다르면 문서가 맞다.

## 순서

**1. 갈림길을 찾는다.** 테스트할 가치 = 갈림길이 있는가. `if`, 에러 처리, 폴백, 경계값, "옛 형식도 받아줘야 한다" 같은 겉으로 안 보이는 약속. 넘겨주기만 하는 코드(위임, 단순 매핑)는 테스트하지 않는다. 확인할 게 "목을 불렀는가"뿐인 테스트는 빈 테스트다.

**2. 갈림길마다 이름을 먼저 쓴다.** 한국어 "~하면 ~한다".

```ts
it('실패 응답이면 서버가 준 메시지로 에러를 던진다', ...)
it('사용자가 없으면 게스트로 폴백한다', ...)
```

이름만 읽어도 뭘 검증하는지 보여야 한다. `it('parse test')` 금지. 이름이 안 써지면 갈림길이 아직 안 보이는 것이다.

**3. 실패하는 테스트를 쓴다.** Given → When → Then. 단락은 빈 줄로. 자명하면 주석 없이.

```ts
it('사용자가 없으면 게스트로 폴백한다', () => {
  const repo = { find: () => null };

  const user = getUserOrGuest(repo, 1);

  expect(user.role).toBe('guest');
});
```

한 테스트에 when-then 사이클은 하나. 두 번째가 생기면 쪼갠다. 입력만 다른 같은 흐름은 `it.each` 표로 묶는다(`%s`에는 문자열 컬럼만).

**4. 그 파일만 돌려 실패를 본다.** 빨간불을 보지 않고 구현으로 가면 테스트가 뭘 지키는지 모른다.

```bash
pnpm --filter web exec vitest run 경로/파일.test.ts
pnpm --filter mobile exec jest 경로/파일.test.ts
```

**5. 통과시킨다.** 최소 구현. 테스트가 요구하지 않는 것은 쓰지 않는다.

**6. 마지막은 루트에서.**

```bash
pnpm test
```

`--filter web`만 돌리면 `packages/analytics`·`packages/bridge`를 건너뛴다. `analytics`의 `events.test.ts`가 이벤트 이름 컨벤션(Title Case, 과거형 `-ed`, 중복·숫자 금지)을 테스트로 강제하는데, 이걸 안 돌려 CI가 빨간불로 올라간 PR이 둘 있었다.

## 어디에 두나

소스 옆. `foo.ts` 옆 `foo.test.ts`, `Foo.tsx` 옆 `Foo.test.tsx`. 테스트 파일도 층 규칙을 따른다 — `shared`의 테스트가 `features`를 import하면 방향 위반이다. 여러 슬라이스를 함께 꽂아 보는 통합 테스트는 배선의 주인(`app/`) 옆에.

## 화면 테스트

모양이 아니라 동작. 사용자가 하는 방식으로 조작하고 결과만 확인한다.

- 찾기는 `getByRole`, `getByText`. `getByTestId`는 최후 수단. 클래스·마크업 검사 금지.
- "안 보인다"는 `queryBy...`로. `expect(screen.queryByText('탈퇴')).not.toBeInTheDocument()`.
- 스냅샷 테스트 금지. 디자인만 바뀌어도 깨지고 아무도 diff를 읽지 않는다.

## 목

**경계만.** fetch, 네이티브 SDK(브릿지·햅틱·알림), 시간. 우리 내부 모듈까지 목하면 목끼리 대화하는 테스트가 된다. 목이 3개 이상 필요하면 설계를 의심한다 — 테스트하기 어려운 것은 대개 관심사가 섞인 것이다.

- 목은 매 테스트 자동 초기화된다(web·mobile 설정에 켜져 있음). 수동 `clearAllMocks`는 안 써도 된다.
- 시간은 fake timer. `vi.useFakeTimers()` → `vi.advanceTimersByTime(ms)` → `afterEach(() => vi.useRealTimers())`. 진짜로 기다리지 않는다.
- mobile은 `vi.`를 `jest.`로.

### 난수 목 함정

"원하는 값이 나올 때까지 다시 뽑는" 코드(rejection sampling)에 **상수 난수 목**을 주면 영원히 안 끝난다. `do { next = floor(rand()*len) } while (next === current)`에 `() => 0.4`를 주면 후보가 계속 같다. 이걸로 vitest가 "RUN 뒤 멈춤"이 됐고, 환경 탓으로 오판해 CI 15분 타임아웃까지 갔다.

- 테스트가 멈추면 환경보다 **내 테스트의 무한 루프·재귀**부터 의심한다. 해당 파일만 격리 실행해 좁힌다.
- 뽑는 코드 자체를 루프 없는 산식으로 짜면(`(current + 1 + floor(rand() * (len - 1))) % len`) 어떤 목에도 안전하다.
- vitest 여러 개를 동시에 돌리지 않는다. 워커가 겹쳐 CPU가 물린다.

## 버그 수정

재현 테스트부터. "이 입력이면 이렇게 잘못된다"를 테스트로 만들어 빨간불을 보고, 고쳐서 초록불. 코드래빗 지적을 반영할 때도 같다. 재현 테스트 없이 고친 수정은 다음에 같은 방식으로 다시 깨진다.

## 보고

테스트를 쓰고 나면 무엇을 지키는지 이름으로 말한다. "테스트 3개 추가"가 아니라 "없으면 게스트 폴백, 실패 응답 메시지, 옛 형식 호환 — 셋을 테스트로 고정". 실행 결과(통과 수, 실패하면 출력)를 그대로 보고한다. 돌리지 않았으면 돌리지 않았다고 말한다.

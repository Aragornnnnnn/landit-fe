# 프론트엔드 근본 전략 카탈로그

토스 프론트엔드 근본 "좋은 코드를 위한 4가지 기준"의 전략 17개를 landit 코드에 대 볼 수 있게 줄인 것이다. 리뷰에서 걸린 항목이 어느 전략에 해당하는지 찾고, 보고서에 전략 이름을 적을 때 쓴다.

각 항목은 세 줄이다. **냄새**(무엇이 보이면 의심하나), **처방**(원문이 권하는 수정), **landit에서**(이 레포에서 그 냄새가 나는 자리). 원문의 예시 코드는 옮기지 않고 상황만 풀어 적었다.

## 가독성 — 읽는 사람이 한 번에 들고 있어야 할 맥락이 몇 개인가

### 같이 실행되지 않는 코드 분리하기

- **냄새** — 권한·상태에 따라 갈라지는 두 경로가 한 컴포넌트 안에서 `if`·삼항·`useEffect` 가드로 교차한다. 읽는 사람은 자기와 무관한 경로까지 머리에 올린다.
- **처방** — 분기를 최상위 한 곳으로 모으고, 각 경로를 이름 있는 컴포넌트로 뗀다. 각 컴포넌트는 분기 하나만 안다.
- **landit에서** — 프리미엄/무료, 시나리오/스몰톡, 셸 안/브라우저 단독 같은 축으로 갈라지는 화면. 한 컴포넌트에 `isPremium ?`이 세 번 이상 나오면 여기다.

### 구현 상세 추상화하기

- **냄새** — 흐름을 읽는 자리(페이지·지휘자 훅)에 세부 구현이 그대로 펼쳐져 있다. 로그인 확인 후 이동, 확인 다이얼로그 열고 결과 따라 전송 같은 것을 다 읽어야 이 컴포넌트가 뭘 하는지 안다.
- **처방** — 한 겹 안으로 밀고 이름으로 부른다. 가드는 래퍼 컴포넌트로, 버튼과 그 클릭 뒤 로직은 한 컴포넌트로 묶는다. 사람이 한 번에 드는 맥락은 6~7개가 한계다.
- **landit에서** — `page.tsx`는 파라미터 해석과 조립만 한다는 규칙이 이것이다. 게이트(로그인·구독·온보딩 완료)를 페이지 본문에 인라인으로 두면 여기 걸린다.

### 로직 종류에 따라 합쳐진 함수 쪼개기

- **냄새** — "이 페이지의 쿼리 파라미터 전부", "이 화면의 상태 전부"처럼 종류로 묶인 훅. 책임이 무한히 늘어나고, 하나만 쓰는 컴포넌트도 전부에 묶인다.
- **처방** — 파라미터·상태 하나마다 훅 하나. 이름이 구체적으로 바뀌고 영향 범위가 좁아진다.
- **landit에서** — 커스텀 훅 하나는 관심사 하나라는 규칙. `use{화면}State` 같은 이름이 보이면 안에 몇 종류가 들어 있는지 세라.

### 복잡한 조건에 이름 붙이기

- **냄새** — `filter`·`some`·`&&`가 여러 단계로 중첩된 익명 조건식. 조건이 뜻하는 바를 따라가야만 안다.
- **처방** — 조건을 `isSameCategory`·`isPriceInRange`처럼 이름 있는 불리언으로 쪼갠다. 단순하거나 한 번만 쓰는 조건은 그대로 둬도 된다.
- **landit에서** — 잠금·표시 여부 판정(`canLockPaywall`, `replayAllowed`처럼 단일 술어로 뽑은 선례가 있다). JSX 안 `{a && !b && c.length > 0 && ...}`가 걸린다.

### 매직 넘버에 이름 붙이기

- **냄새** — `delay(300)`, `length > 155`처럼 맥락 없는 숫자. 애니메이션 대기인지, 서버 반영 대기인지, 지우다 만 테스트 코드인지 모른다.
- **처방** — `ANIMATION_DELAY_MS`처럼 단위까지 담은 이름의 상수로.
- **landit에서** — 발화 길이 임계값, 스냅 임계값, 재시도 횟수, 타임아웃. 숫자에 단위 접미사(`_MS`, `_PX`, `_CHARS`)가 없으면 의심.

### 시점 이동 줄이기

- **냄새** — 버튼 하나가 왜 비활성인지 알려면 `policy.canInvite` → `getPolicyByRole` → `POLICY_SET`으로 위아래 세 번 뛰어야 한다. 간단한 규칙에 추상화 층이 겹쳐 있다.
- **처방** — 조건을 요구사항 그대로 펼치거나(`switch`), 한눈에 보이는 객체 리터럴로 그 자리에 둔다. 권한 체계가 정말 복잡할 때만 층을 둔다.
- **landit에서** — 두 단계 이상의 "테이블에서 찾아 → 매핑 → 소비" 체인. 표(상태 → 문구·색)가 소비처와 다른 파일에 있으면 같이 고쳐야 할 것이 떨어져 있는 것이기도 하다.

### 삼항 연산자 단순하게 하기

- **냄새** — 삼항 안에 삼항. 어떤 조건으로 어떤 값이 나오는지 한눈에 안 보인다.
- **처방** — `if`를 차례로 세운 즉시 실행 함수나 이른 반환으로 펼친다.
- **landit에서** — JSX 안 중첩 삼항이 대부분. 세 갈래 이상이면 분기별 컴포넌트나 상태 → 노드 매핑으로.

## 예측 가능성 — 이름·파라미터·반환값만 보고 동작을 맞힐 수 있나

### 이름 겹치지 않게 관리하기

- **냄새** — 라이브러리의 `http`를 감싼 우리 모듈도 `http`다. 부르는 사람은 단순 GET을 기대하지만 토큰 조회가 끼어든다.
- **처방** — 라이브러리와 구분되는 이름(`httpService.getWithAuth`)으로. 이름이 추가 동작을 말하게 한다.
- **landit에서** — 웹 플랫폼·라이브러리 어휘와 같은 이름을 쓰면서 동작을 바꾼 래퍼. 한 개념 한 단어 규칙의 반대면이다. 같은 단어를 다른 뜻으로 쓰지 마라.

### 같은 종류의 함수는 반환 타입 통일하기

- **냄새** — 서버 상태 훅 하나는 `Query` 객체를, 하나는 `data`만 돌려준다. 검증 함수 하나는 불리언을, 하나는 `{ ok, reason }`을 돌려준다. 쓸 때마다 확인해야 하고, `if (checkIsAgeValid(age))`처럼 항상 참인 분기가 생긴다.
- **처방** — 같은 종류면 같은 모양. 검증은 `{ ok: true } | { ok: false; reason }` 판별 유니온으로.
- **landit에서** — `Query`/`Mutation` 접미사 훅은 useQuery 결과를 그대로 돌려준다는 약속이 이것이다. 하나만 `data`를 풀어서 주면 걸린다.

### 숨은 로직 드러내기

- **냄새** — `fetchBalance`가 잔액을 가져오면서 로깅도 한다. 이름·파라미터·반환값 어디에도 없는 일이 일어나고, 로깅이 죽으면 조회도 죽는다.
- **처방** — 이름으로 예측되는 일만 구현에 남기고, 부수 동작은 호출부로 올린다.
- **landit에서** — 조회 훅 안의 앰플리튜드 `track`, api 함수 안의 Sentry 캡처나 토스트, 세터 안의 라우팅. `packages/analytics` 호출은 사건이 일어난 자리(클릭·완료 콜백)에 둔다.

## 응집도 — 같이 고쳐야 하는 코드가 같이 있나

### 함께 수정되는 파일을 같은 디렉토리에 두기

- **냄새** — `components/`·`hooks/`·`utils/`처럼 종류별로 가른 디렉토리. 무엇이 무엇을 참조하는지 안 보이고, 기능을 지울 때 조각이 남는다.
- **처방** — 함께 바뀌는 파일끼리 도메인 디렉토리로. `../../../Domain2/hooks/useFoo` 같은 import가 보이면 잘못된 참조임을 바로 안다.
- **landit에서** — 3층(app → features → shared) 배치와 "이 화면에서만 쓰나"로 자리 정하기가 이것이다. `features` 간 가로 import는 경계를 넘었다는 신호다.

### 매직 넘버 없애기

- **냄새** — 가독성의 매직 넘버와 같은 코드를 다른 각도로 본다. `delay(300)`이 애니메이션 길이와 짝인데 애니메이션만 바꾸면 조용히 깨진다.
- **처방** — 짝이 되는 값을 한 상수로 묶어 같이 바뀌게 한다.
- **landit에서** — 모션 토큰의 duration과 그걸 기다리는 타이머, 스트립 여백과 placeholder 크기처럼 짝 규칙이 있는 값. 한쪽만 고치면 어긋나는 값이 두 파일에 따로 있으면 걸린다.

### 폼의 응집도 생각하기

- **냄새** — 폼을 필드 단위로 관리할지 폼 전체 단위로 관리할지 정하지 않아, 검증이 필드에도 있고 스키마에도 있다.
- **처방** — 변경 단위가 필드면 필드 단위(독립 검증·재사용), 폼 전체면 전체 단위(단일 기능·단계별 입력·필드 간 의존). 둘 중 하나를 고른다.
- **landit에서** — 설문, 영어 수준 체크, 온보딩 스텝처럼 여러 입력이 한 제출로 모이는 화면. 단계별 입력은 전체 단위가 맞다.

## 결합도 — 이걸 고치면 어디까지 영향이 가나

### 책임을 하나씩 관리하기

- **냄새** — 가독성의 "종류로 합쳐진 훅"과 같은 코드를 영향 범위로 본다. 페이지의 여러 컴포넌트가 한 훅에 매달려, 훅을 고치면 전부 흔들린다.
- **처방** — 책임 하나에 훅 하나. 영향 범위가 그 책임을 쓰는 곳으로 좁아진다.
- **landit에서** — 지휘자 훅(`useScenarioTalkFlow` 등)은 예외로 인정한 자리다. 그 밖의 훅이 관심사 둘 이상을 들고 있으면 걸린다.

### 중복 코드 허용하기

- **냄새** — 여러 페이지에서 비슷해 보여 공통 훅으로 뽑았는데, 페이지마다 로깅 값·닫기 동작·문구가 달라질 여지가 있다. 고칠 때마다 인자가 늘고 모든 사용처를 다시 테스트한다.
- **처방** — 앞으로도 같이 변할 것이 확실할 때만 묶는다. 갈릴 여지가 있으면 중복을 둔다. 지금 닮았다는 사실은 근거가 아니다.
- **landit에서** — "미리 일반화하지 않는다", "두 번째 사용처가 생기면 내린다" 규칙. 호출자 하나를 위해 공용 컴포넌트에 프롭·옵션을 늘리는 것도 같은 병이다. 단, 같은 슬라이스 안에서 방금 복사한 글자 단위 복붙은 "갈릴 여지"가 아니라 그냥 복붙이다.

### Props Drilling 지우기

- **냄새** — 부모가 받은 `items`·`onConfirm`을 중간 컴포넌트가 쓰지도 않으면서 자식에게 넘기기만 한다. prop 이름 하나 바꾸면 중간 전부를 고친다.
- **처방** — 먼저 조합(`children`)으로 중간 층을 없앤다. 트리가 깊어 그래도 남으면 그때 Context. Context는 마지막 수단이다.
- **landit에서** — 화면 `_ui/` 안에서 세 단계 이상 내려가는 prop. 중간 컴포넌트의 props 목록에 자기가 안 쓰는 이름이 있으면 걸린다.

## 축끼리 충돌한다

원문이 스스로 말하는 것이다. 응집도를 올리려고 공통화·추상화하면 가독성이 떨어지고, 중복을 허용하면 결합도는 낮아지지만 응집도가 떨어진다. 어느 쪽도 그 자체로는 틀리지 않는다. 함께 수정되지 않으면 오류가 나는 경우에는 응집도를, 위험이 크지 않으면 가독성과 결합도를 우선하라는 것이 원문의 기준이다.

# 코드 퀄리티 — 프론트엔드 근본 4기준 챙기기

## 무엇을 챙기나

좋은 프론트엔드 코드는 **변경하기 쉬운** 코드다. 토스 프론트엔드 근본은 그걸 네 기준으로 판단한다.

- **가독성** — 읽는 사람이 한 번에 머릿속에 드는 맥락이 적고, 위에서 아래로 읽힌다.
- **예측 가능성** — 이름·파라미터·반환값만 보고 동작을 맞힐 수 있다.
- **응집도** — 같이 수정돼야 할 코드가 반드시 같이 수정되게 구조가 받쳐 준다.
- **결합도** — 코드를 고쳤을 때 영향 범위가 좁고 예측된다.

원문의 전략 17편 중 코드를 보고 바로 판별할 수 있는 것을 15개로 추렸다(매직 넘버와 종류별로 합쳐진 훅은 두 축에서 같은 코드를 보는 것이라 하나로 합쳤다). 아래 표가 챙길 것의 전부다. 항목 이름은 원문 전략 이름 그대로다. 항목마다 **코드에서 보이는 신호**와 **처방**을 적었다. 표는 원문 기준으로만 적었다. landit에서 그 냄새가 나는 자리는 `references/frontend-fundamentals.md`에만 있다. 걸린 항목이 어느 전략인지 확인할 때, 그리고 landit의 어느 코드가 그 모양인지 떠올릴 때 연다.

## 기준끼리 충돌한다 — 판정 규칙

네 기준을 한꺼번에 다 만족하기는 어렵다. 원문이 스스로 말하는 것이다.

- 공통화·추상화하면 **응집도가 오르고 가독성이 내려간다.**
- 중복을 허용하면 **결합도가 내려가고 응집도가 내려간다.**

그래서 표의 항목에 걸렸다고 바로 "고쳐라"가 아니다. 원문의 기준은 이것이다.

> 함께 수정되지 않으면 오류가 나는 경우에는 응집도를 우선해 공통화·추상화하고, 위험이 크지 않으면 가독성을 우선해 중복을 허용한다.

판정할 때는 이 순서로 묻는다.

1. 이 코드가 어느 기준에서 나빠졌나.
2. 그 대가로 얻은 기준이 있나.
3. **이 코드들은 앞으로도 같이 변할 것인가.** 같이 변하면 묶는다. 따로 변할 여지가 있으면 중복을 둔다. 지금 닮았다는 사실은 근거가 아니다.
4. 얻은 기준 없이 그냥 나빠진 것만 "고칠 것"이다. 나머지는 "의도로 인정"이거나 "판단이 갈리는 것"이다.

같은 슬라이스 안에서 방금 복사한 글자 단위 복붙은 "앞으로 갈릴 것"이 아니라 그냥 복붙이다. 3번 질문을 복붙의 면죄부로 쓰지 마라.

## landit에서는 여기에 규칙이 더 얹혀 있다

원문의 기준을 landit이 이미 규칙으로 굳혀 둔 것이 있다. 리뷰 전에 바뀐 파일이 속한 문서를 읽어라. 체크 항목을 여기 복사하지 않은 이유는 갈라지기 때문이다.

- `apps/web/AGENTS.md` — 3층 배치(app → features → shared), "이 화면에서만 쓰나"로 자리 정하기, `utils.ts`·`helpers.ts`·`types.ts`·`constants.ts` 금지, `features` 간 가로 import, `Query`/`Mutation` 접미사, `handle~` 금지와 `on{사건}`, 한 개념 한 단어, 미리 일반화·승격하지 않기
- `apps/mobile/AGENTS.md` — 위젯 상태 판정 단일 지점
- `AGENTS.md`(루트) — 수동 메모이제이션 금지(React Compiler)

이 규칙들은 표의 항목이 landit 코드에 구체화된 것이다. 규칙 위반은 그 규칙을 출처로 적고, 원문 전략과 같은 냄새면 전략 이름도 같이 적는다.

## 절차

**1. 범위를 잡는다.**

```bash
git status --porcelain
git diff --stat origin/develop...HEAD
```

워크트리에서 스택 PR 작업 중이면 base가 `origin/develop`이 아닐 수 있다. `git log --oneline -5`로 실제 base를 확인한다. 이미 머지된 PR을 보려면 `git diff <머지커밋>^1...<머지커밋>^2`처럼 점 세 개로 본다. 점 두 개로 보면 그 사이 develop에 들어온 남의 변경이 "삭제"로 섞인다.

이번 변경이 만든 문제만 본다. 원래 있던 부채는 언급하되 "이번 것 아님"으로 표시한다. 테스트 파일도 같은 기준으로 본다. 다음 사람은 테스트에서 규칙을 읽는 일이 많다.

**2. 주변을 읽는다.** diff만으로는 응집도와 결합도가 안 보인다. 새 파일은 형제 폴더를, import는 경로를 따라가 본다. 바뀐 함수를 쓰는 다른 호출부도 연다. "의도로 인정"과 "이번 것 아님"은 다른 호출부를 봐야 가를 수 있다. 중간 컴포넌트의 props가 drilling인지는 자식까지 열어 봐야 안다.

**3. 표를 기준별로 한 번씩 통과한다.** 각 항목의 "신호"가 바뀐 코드에 있는지 본다. 없으면 없다고 넘어간다. 네 기준을 다 채우려 하지 마라. 가독성만 걸리는 변경이 대부분이다.

**4. 걸린 것마다 위 판정 규칙을 적용한다.** 고칠 것 / 의도로 인정 / 판단이 갈리는 것으로 나눈다.

**5. 항목마다 전략 이름을 붙인다.** `references/frontend-fundamentals.md`에서 같은 냄새의 전략을 찾아 그 이름을 적는다. 받는 사람이 어느 전략인지 알면 "왜"를 내 말이 아니라 기준으로 확인할 수 있다. 냄새가 실제로 같을 때만 붙인다. 이름만 비슷한 전략을 갖다 붙이면 신뢰를 깎는다. 원문에 없는 냄새(항상 참인 분기, 쓰이지 않는 파라미터처럼 시그니처가 거짓말하는 것)는 기준만 적고 전략 이름은 비워 둔다.

**설계 단계에서 불렸으면** 절차 대신 표를 쓴다. 만들려는 컴포넌트·훅에 대해 "이 항목의 신호가 생길 자리가 있나"를 미리 묻고, 걸리는 항목의 처방을 설계에 반영한다. 특히 분기 분리·책임 하나·폼 단위는 나중에 고치기 비싸므로 처음에 정한다.

## 보고 형식

점수·등급·개수 집계는 하지 않는다. 억지 항목만 생긴다.

```
## 코드 퀄리티 리뷰

**고칠 것**

- `경로:줄` — 무엇이 보이나 (기준 · 전략 이름)
  {얻은 것 없이 나빠진 근거}
  → {처방을 이 코드에 적용한 구체적 수정}

**의도로 인정**

- `경로:줄` — {기준A}를 내주고 {기준B}를 얻었다. {같이 변하지 않을 것 같아서 / 두 번째 사용처가 없어서} 지금은 이게 맞다. (전략 이름)

**판단이 갈리는 것**

- `경로:줄` — {질문}. 앞으로 {조건}이면 묶는 게 맞고, 아니면 지금이 맞다.

**이번 것 아님**

- `경로:줄` — {원래 있던 부채}. 이번 변경으로 눈에 띄었을 뿐이다. (기준 · 전략 이름)
```

비는 덩어리는 제목째로 뺀다. 걸린 게 없으면 "네 기준 다 통과" 한 줄로 끝낸다. 없는 지적을 만들지 마라. 이 리뷰의 가치는 걸러내는 데 있다.

## 고칠 것을 어떻게 처리하나

기본은 **보고하고 멈추는 것**이다. 구조 변경은 되돌리기 비싸고, 어느 기준을 택할지는 사용자의 판단이다.

예외는 기계적인 것 — 매직 넘버 상수화, 조건에 이름 붙이기, 중첩 삼항 펼치기, `handle~` 개명. 이건 고치고 나서 무엇을 고쳤는지 말한다. 수정 후에는 루트에서 `pnpm test`를 돌린다(`--filter web`만 돌리면 `packages/analytics` 컨벤션 테스트를 놓친다). 그리고 고친 부분을 한 번 더 훑는다. 리뷰 중에 손댄 코드는 리뷰를 안 받은 코드다.

## 여기서 다루지 않는 것

널 체크, 에러 처리, 타입 안전성, BE 응답 형태, 회귀는 네 기준 어디에도 속하지 않는다. 코드래빗이 PR에서 본다. 훑다가 눈에 걸리면 그 자리에서 고치거나 보고서 끝에 "축 밖에서 걸린 것"으로 따로 적되, 기준 항목으로 올리지 마라. 성능 일반론("메모이제이션하면 빠를 것")도 다루지 않는다. React Compiler가 켜져 있어 수동 메모이제이션은 금지다.
